          4. Learn: how to think like a SOC analyst

          A repeatable triage workflow

          1. Identify the event. What Event ID is it, and which log did it come from?
          2. Understand what happened. Read the message and work out what Windows is telling you.
          3. Identify the affected user or system. Who or what was involved?
          4. Determine whether the activity is expected. Does it fit this host, this account, and this time of day?
          5. Look for related events. What happened immediately before and after it?
          6. Correlate authentication and privilege activity. Failures, successes and permission changes often only make sense together.
          7. Gather additional evidence. Other logs, MFA records, endpoint telemetry, change tickets, and the person who owns the account.
          8. Decide whether escalation is required. If you cannot explain the activity, pass it on with the evidence you have collected.
          One security event rarely tells the entire story. Analysts build context by correlating multiple events.
          A detection is a reason to investigate, not proof that an attacker is present.

          Detection, correlation and false positives

          A detection is a rule that says "this pattern is worth a look". A correlation combines several events into a story, which is usually far more informative than any single event.

          A false positive is a detection that fires on legitimate activity. They are normal and expected. A forgotten password produces repeated failures. A helpdesk technician legitimately adds a user to a privileged group. A backup product clears logs during maintenance. The skill in triage is not avoiding false positives entirely — it is being able to explain what you checked and why you were satisfied, or why you escalated.

          This tool deliberately explains possible benign causes for every finding. That is what a real analyst does before escalating.

          How to collect Windows events with Event Viewer

          1. Press Win + R, type eventvwr.msc and press Enter.
          2. In the left pane, expand Windows Logs and click Security.
          3. Optionally click Filter Current Log… and enter the Event IDs you want (for example 4624,4625,4720,4732,1102).
          4. With the log or filter selected, choose Action → Save All Events As… and set Save as type to CSV.
          5. Open this tool and upload that CSV file.

          Honest note: Event Viewer's own CSV export has real limitations. It can be slow on large log sets, its column headers are translated on non-English Windows installations, and the useful detail (account, logon type, source IP) is embedded inside a multi-line "Message" column rather than in separate columns. For Event ID 4104 (PowerShell) you must export the Applications and Services Logs → Microsoft → Windows → PowerShell → Operational log, and for 7045 the System log; Event Viewer's Save dialog exports one log at a time. See the README for a PowerShell export command that produces all of these in one consistent file, which is the more reliable route.

          5. Privacy, disclaimer and limitations

          Privacy architecture

          Your Windows security logs are analysed locally in your browser. Files are not uploaded or transmitted anywhere.

          • There is no server, no backend, no database and no cloud service.
          • The application makes zero network requests. It contains no analytics, tracking, cookies, advertising or telemetry.
          • Uploaded files are read into memory only. They are not stored, not written to disk, and not retained after you close the tab.
          • Nothing is sent to any AI provider or external API, because no such code exists in this project.
          • You can verify this: open script.js and search for fetch, XMLHttpRequest, sendBeacon and WebSocket. They appear only inside comments explaining why they are not used.

          Disclaimer

          Educational SOC triage tool. Findings indicate activity that may deserve investigation and do not prove malicious behaviour.

          Only analyse logs from systems you own or are authorised to investigate.

          Severity in this tool describes investigative priority, not certainty. The word "Critical" is deliberately not used.

          Known limitations

            Windows Security Event Log Triage Tool — an educational project. Runs entirely offline in your browser. No data leaves this page.

            2. Thresholds

            Security thresholds vary by environment. These values are educational defaults rather than universal SOC detection rules.

            Number of failed logons (Event ID 4625) for the same account before an alert is raised. Default: 5.

            Failures must fall inside this window to be treated as a single burst. Default: 10 minutes. If your export has no usable timestamps, the tool falls back to whole-dataset grouping and says so.
