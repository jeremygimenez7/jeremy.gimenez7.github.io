Network Traffic Triage Tool - Wireshark CSV Analysis

A static browser application that turns a Wireshark packet-list CSV export into a readable network activity report. Six transparent threshold rules flag activity worth investigating, explain their own reasoning, and leave the judgement to the analyst. No AI, no machine learning and no packet data leaving the browser.

HTML CSS Vanilla JavaScript CSV parser written from scratch Local-only analysis

01 · Overview

Project overview

Detection tells an analyst where to look. Investigation determines what actually happened. An anomaly is a starting point for investigation, not proof of compromise. No alerts does not mean a capture is safe.

Wireshark is excellent at showing you packets and poor at telling you what to pay attention to. This project fills that gap for learning purposes: export the packet list as CSV, load it, and get counts, the busiest endpoints, a protocol breakdown and a small set of clearly-explained alerts.

It deliberately avoids the "AI detects hackers" style of tool. There is no probability of compromise, no risk score presented as certainty, and no claim that any single pattern proves anything. The rules use simple, inspectable counts, and the thresholds are adjustable so you can see how a configuration choice changes the result without changing the underlying evidence.

Objectives

  • Practise the analyst workflow: observe, identify, classify, corroborate, decide.
  • Make every alert explain itself, including the innocent explanation that could account for it.
  • Write a CSV parser from scratch, including quoted commas, escaped quotes and multiline fields.
  • Keep the whole thing dependency-free and genuinely offline.
  • Test the parser and the rule boundaries, not just the happy path.
02 · Detection rules

Six threshold rules, all adjustable

Every rule triggers on more than, not equal to, its threshold. Counts cover the entire imported export, not a time window.

High Packet Volume

Default: > 50 packets per source · Priority: Low

Counts packets sent by a single source address. A busy server, a backup job or a software update can legitimately produce the same figure.

Possible Network Scanning

Default: > 10 distinct destinations · Priority: Medium

Counts distinct numeric destination addresses contacted by one source. Authorised vulnerability scans and monitoring probes look similar.

Possible Port Scanning

Default: > 10 distinct ports · Priority: Medium

Counts distinct inferred destination ports per source/destination pair. Ports are only read from TCP/UDP rows with a numeric port pair in the Info field.

High ICMP Activity

Default: > 30 ICMP packets · Priority: Medium

Counts ICMP and ICMPv6 packets per source. Ping sweeps and network troubleshooting both produce this pattern.

High DNS Activity

Default: > 30 DNS packets · Priority: Low

Counts DNS-labelled packets per source. It includes replies, so it does not prove high query volume, domain abuse or beaconing.

Repeated Communication

Default: > 40 packets per pair · Priority: Low

Counts packets for a directional source-to-destination pair and reports the most common protocol. Repeated traffic does not establish periodicity.

These are educational defaults, not universal security thresholds. A busy server may legitimately generate thousands of packets while the same activity from another endpoint deserves investigation. Capture duration, host role, normal workload and expected applications all matter.

03 · Workflow

From Wireshark to a triage report

1

Capture

  • Open Wireshark and capture only traffic you own or are authorised to monitor.
  • Stop the capture when you have enough data.
  • Keep real captures out of synced folders if their contents are sensitive.
2

Export as CSV

  • Use the packet-dissections / packet-list CSV export and keep the column headings.
  • Check whether you are exporting all packets or only the displayed ones.
  • Export the CSV, not a PCAP - this tool does not parse captures.
3

Load it

  • Choose the file or drag it onto the page.
  • UTF-8 CSV only, up to 10 MiB / 50,000 packet rows.
  • Malformed input produces a clear error rather than a partial report.
4

Triage

  • Read the overview: totals, busiest endpoints, protocol distribution.
  • Check the analysis-coverage list, which states what could not be calculated.
  • Adjust thresholds and re-apply to see how the verdict changes.
04 · Privacy & security

Privacy and security design

A packet list can expose internal addresses, hostnames, usernames and services. The tool is built so that none of it is transmitted, and so that the browser itself enforces that rather than relying on a promise.

Enforced in the page itself

  • The page carries a strict Content-Security-Policy header: default-src 'none', script-src 'self', connect-src 'none'.
  • That policy makes the browser refuse outbound requests from the page, so a network call could not succeed even if it were added by mistake.
  • The uploaded CSV stays in memory and is never sent anywhere.
  • No cookies, no analytics, no external fonts or images.

Safe handling of untrusted input

  • Every value taken from the CSV is written into the page as text, never as HTML.
  • Injected markup in a CSV field renders as visible text instead of running.
  • The CSV parser handles quoted commas, escaped double quotes and multiline quoted fields.
  • Decisions that cannot be made safely produce a warning, not a guess.

Only analyse traffic from systems and networks you own or are authorised to monitor. Use the fictional sample captures for demonstrations rather than exposing real users, addresses or hostnames.

05 · Explainability & testing

Samples, explanations and tests

Three fictional captures

  • Normal traffic - 18 packets, no alerts. No alerts is not proof of safety.
  • High-volume traffic - 60 packets, producing one High Packet Volume alert for 10.0.0.25.
  • Mixed SOC lab - 176 packets, seven alerts covering all six rules.

All three use documentation-only address ranges and invented hostnames.

Every alert explains itself

  • Which rule fired, the threshold used and the count that exceeded it.
  • The specific packets or addresses that produced the count.
  • A suggested line of investigation.
  • The ordinary activity that could account for the same pattern.

Priority represents where to investigate, not certainty or business impact.

The parser and the rule engine are covered by a dependency-free browser test suite at tests/tests.html. It covers parser edge cases, threshold boundaries, the three sample captures and the safe rendering of alert text, and reports pass or fail in the page. It needs no special browser flags and no installation.

06 · Limitations

What this tool cannot tell you

A CSV export is not a packet capture, and this tool is honest about what that costs it.

Data limitations

  • CSV lacks much of the information a PCAP contains.
  • Encrypted traffic limits payload visibility.
  • NAT, resolved names, IPv6 spellings and shared systems all complicate attribution.
  • Protocol labels are Wireshark's interpretation, not ground truth.
  • Semicolon-delimited and UTF-16 exports are not supported.

Analytical limitations

  • Packet volume alone does not establish malicious behaviour.
  • No time-window analysis, baselining or retransmission de-duplication.
  • Repeated communication does not establish periodicity or beaconing.
  • No direction-of-session inference and no capture-integrity verification.
  • It does not replace Wireshark, an IDS, a SIEM or professional network monitoring.
