Windows Security Event Log Triage Tool - SOC-Style Log Analysis

A static browser application that reads a Windows Event Viewer Security-log CSV export and produces a plain-English triage report: what happened, why it might deserve investigation, what ordinary activity could explain it, and what to check next. Every finding carries an itemised score showing exactly why each point was awarded.

01 · Overview

Project overview

An educational SOC triage tool. Findings indicate activity that may deserve investigation and do not prove malicious behaviour. Only analyse logs from systems you own or are authorised to investigate.

Windows security logs are dense. A single export can contain thousands of ordinary logons, and the interesting events are invisible until you know what to look for and how to link events together. This tool exists to make that reasoning explicit.

It is deliberately not a fake "AI detects hackers" product. There is no probability of compromise, no severity of "Critical", and no claim that any single event proves an intrusion. It teaches four things instead:

What the project teaches

  • How Windows security events work - what event 4624 actually records, why the logon type changes its meaning, and why the same event behaves differently on a workstation and a server.
  • How analysts correlate events - why three failed logons followed by a success is a more interesting object than four separate rows.
  • How false positives happen - every finding lists the ordinary explanations, because most alerts in a real SOC have one.
  • How to decide what deserves investigation - using a transparent score where each point is shown next to the reason it was awarded.
02 · Event coverage

Ten Windows Event IDs, explained

Ten Event IDs, learned properly, are worth more than a thousand skimmed. The tool recognises and explains this set rather than guessing at everything else.

Authentication events

4624 · Successful logon 4625 · Failed logon 4672 · Special privileges assigned

The tool extracts the account, logon type, source IP, workstation, process and failure reason, because a logon type 5 service account is very different from a logon type 2 person at a keyboard.

Account and privilege changes

4720 · User account created 4726 · User account deleted 4728 · Added to a global group 4732 · Added to a local group

Membership of a privileged group escalates a finding, because creating an account and then granting it power is a recognised persistence pattern.

Execution and defence evasion

4688 · Process created 4104 · PowerShell script block

Encoded PowerShell raises a finding and the related 4688 process-creation event is attached as supporting evidence rather than being reported separately.

Anti-forensics

1102 · Security audit log cleared

Clearing the security audit log always produces a High finding. There are legitimate reasons to do it, and the finding still says so - but it is never treated as routine.

Deliberately out of scope: scheduled-task events, Sysmon, Defender events, and anything requiring raw .evtx parsing. A narrow tool that explains its own coverage honestly is more useful for learning than a broad tool that pretends to understand everything.

03 · Detection logic

Correlation, not just counting

The interesting part of log analysis is not finding one event. It is noticing that several events belong together.

Repeated authentication failures

Failures are counted per account and source. A count at the threshold is Low; at twice the threshold it becomes Medium, and the finding states which case applied and why.

Failures followed by a success

The high-value pattern. Failures then a success from the same IP inside the window is High. A success from a different IP an hour later is Medium with an explicit "not strong" note, because that is genuinely weaker evidence.

Account creation into privilege

A 4720 followed by a 4732 for the same account is High. The finding shows the sequence and the elapsed time, and it absorbs the standalone "account created" observation so the same activity is never counted twice.

Security log cleared

Event 1102 always produces a High finding. It is one of the few events where the absence of further evidence is itself worth reporting.

Privileged group changes

Administrative and privilege-related group changes are grouped by who made them, so unrelated actors do not get merged into one misleading pile.

Encoded PowerShell

Base64-encoded script blocks are detected, and the related process-creation event is attached as supporting evidence instead of appearing as a separate finding.

04 · Scoring model

An itemised score, not a black box

Findings are graded as Informational, Low, Medium or High. Alongside the grades, each finding contributes a number of points, and the interface itemises every contribution with the reason it was awarded. When the total exceeds the maximum, the score is capped at 100 and the cap is disclosed rather than hidden.

The score exists to order investigation effort. It is not a probability of compromise and it is never presented as one.

Every finding includes

  • What happened, in plain English.
  • The events that support it, with their identifiers.
  • Why it may deserve investigation.
  • The legitimate activity that could explain it.
  • A concrete next step, such as which record to check next.

What it deliberately avoids

  • No probability that a machine is compromised.
  • No "Critical" severity that implies certainty.
  • No hidden weighting or unexplained score.
  • No finding that suppresses its own false positives.
05 · Privacy & security

Your logs stay on your machine

Windows security logs contain usernames, computer names, IP addresses and internal process paths. This tool analyses them locally in the browser. Files are not uploaded or transmitted anywhere, and the README explains how to verify that claim rather than simply asserting it.

Network isolation, demonstrated

  • The whole test suite was re-run with fetch, XMLHttpRequest and sendBeacon replaced by functions designed to fail loudly.
  • No call was ever made, which is evidence rather than a promise.
  • There is no backend, database, cloud service, API key or external dependency.

Hardened against hostile input

  • A test CSV whose account, computer and IP fields contain script and image payloads creates no elements and runs nothing.
  • The payload renders as plain text in the table, the findings and the filter options.
  • Event data is treated as untrusted throughout, because a log export is attacker-influenced content.
06 · Testing

Testing, and the bugs it found

The logic was tested against the documented rule behaviour, the sample datasets and hostile input. The four sample CSV files were also parsed by a second, independently written reader to confirm the files themselves are well formed and that each one produces the same findings as the embedded demo data.

Defects found and fixed

  • The suspicious-service-path check never matched anything. A regular expression had been written with doubled backslashes, so it could never match a real Windows path. A service installed from a user-writable folder was therefore never escalated. Fixed by normalising path separators first.
  • The timeline implied a chronology it could not support. With no usable timestamps, events were still listed under a "Timeline" heading in file order, which could be misread as a time sequence. Fixed by detecting that case and stating the order is the file's, not time's.

Honesty about the test results

  • Two early test failures turned out to be errors in the tests, not the application: an incorrect expected count of successful logons, and an assumed severity threshold the documented rule does not use.
  • Both were corrected in the tests rather than by changing working behaviour, which is the point of writing the expectation down first.
  • No alert was ever produced for the known-good sample beyond informational level.
07 · False positives

Where the findings can mislead

Every finding lists its own legitimate explanations. These are the traps the project documents openly.

Common false positives

  • On a real machine, logon types 3 and 5 (network and service logons by SYSTEM and machine accounts) are extremely common and are not evidence of anything.
  • Administrative activity by a genuine administrator looks identical to administrative activity by an intruder.
  • Scheduled tasks, backup software and monitoring agents generate privileged activity on a timer.
  • Service-installation findings depend on whether process-creation auditing is even enabled.

Scope limitations

  • CSV exports only. Raw .evtx files are not parsed.
  • Scheduled tasks, Sysmon and Defender events are out of scope in Version 1.
  • Localised Windows messages are handled, but the tool warns when it could not read the labels.
  • Without usable timestamps the correlation window cannot be applied, and the tool says so rather than guessing.
  • It teaches triage. It is not a replacement for a SIEM or for an organisation's incident-response process.
