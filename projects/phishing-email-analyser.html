Phishing Email Analyser - Local, Explainable Email Triage

A static web application that reads a suspicious email and explains, in plain English, which phishing and social-engineering warning signs it contains - and exactly how much each one contributed to a risk score from 0 to 100. Optional raw-header analysis adds SPF, DKIM, DMARC and Reply-To checks. Nothing the user pastes ever leaves the browser.

HTML CSS Vanilla JavaScript No dependencies Local-only analysis

01 · Overview

Project overview

This is an educational tool, not a security product. It highlights warning signs and it cannot prove that an email is malicious - or that it is safe. It is built to teach how phishing email is constructed, and to make that reasoning visible instead of hiding it behind a single verdict.

Most phishing advice says "look for the warning signs" without ever showing what those warning signs are made of. This project turns that advice into something you can inspect. You paste an email, and the tool reports each pattern it recognises, the number of points that pattern is worth, and the exact text that triggered it.

The design goal was explainability. There is no hidden weighting, no machine learning and no mystery score. Every rule has a fixed weight, the interface lists which rules fired, and the arithmetic that produced the final number is shown on screen as a table.

Objectives

  • Turn phishing-awareness theory into a tool a beginner can actually use and learn from.
  • Make the scoring model completely open - every point traceable to evidence.
  • Handle real content: clickable HTML links, look-alike domains, attachment names and raw email headers.
  • Prove the privacy claim architecturally: there is no server, so the data has nowhere to go.
  • Write automated tests so the detection logic can be changed safely later.
02 · Scoring model

How the score works, and why it is open

There are 49 checks in total: 40 that read the email text and 9 that only run when raw email headers are supplied. Each check has a fixed weight between 6 and 30 points. The weights of the checks that fire are added together and the total is capped at 100.

The result is placed in one of three bands, and the interface shows the full breakdown - the indicator, its severity, its points and the evidence - plus a totals row, so the number can always be traced back to the text that caused it.

Low Risk · 0-24

Hardly any warning signs found

A low score means the text did not contain the patterns the analyser knows about. It is not a statement that the email is safe.

Suspicious · 25-59

Several warning signs found

Enough indicators are present that the message should be verified independently before anyone acts on it.

High Risk · 60-100

Many strong warning signs

Several high-weight indicators fired together. The guidance is to treat the message as hostile and not interact with it.

Each individual finding is also given a severity label - Very strong (25+ points), Strong (15+), Moderate (10+) or Weak - so the relative importance of the evidence is visible at a glance rather than being flattened into a single total.

03 · Detection coverage

What the analyser looks for

Coverage is grouped into four areas. Header checks are deliberately optional and are never reported as "passed" when the headers were not supplied.

Email text

Urgency & pressure language Very short deadlines Account suspension threats Password requests MFA / one-time code requests Credential-harvesting wording Gift-card & crypto requests Bank-detail change requests Secrecy and "quick favour" BEC wording Unexpected invoice wording Prize and refund bait Macro / enable-editing instructions Generic greetings & impersonation wording

Links

Shortened links Raw IP addresses Abused top-level domains Punycode look-alike domains "@" userinfo trick Brand in the wrong domain Deliberate brand misspellings Long subdomain chains Unencrypted http:// links Link text that lies about the target

Attachment names

Executables & scripts (.exe, .scr, .js, .ps1, .lnk) Macro-enabled documents (.docm, .xlsm, .pptm) Compressed archives (.zip, .rar, .7z) Double extensions (invoice.pdf.exe) Unusual types for email (.html, .svg, .xml)

Raw headers (optional)

SPF fail & softfail DKIM fail DMARC fail Reply-To on a different domain Return-Path mismatch Display name spoofing Replies sent to free webmail No passing authentication at all

If headers are not pasted, the nine header checks are listed as "not checked" - never as passed. A tool that silently marked an unrun check as a success would give false reassurance, which is exactly the failure mode this project set out to avoid.

04 · Privacy architecture

Why the email never leaves the browser

Phishing email contains real credentials, real bank details and real internal conversations. Sending a suspicious message to an online "phishing checker" means handing that content to somebody else's server. This project avoids the problem by having no server at all.

The analyser is a set of static files. All detection, scoring and rendering happen in the visitor's own browser. There is no backend, no database, no account, no AI provider, no API key and no analytics.

How the claim was verified

  • Every shipped file was searched for fetch, XMLHttpRequest, sendBeacon, WebSocket, EventSource, cookies and localStorage.
  • The result was zero matches in the application code.
  • No script, stylesheet, font or image is loaded from another domain.
  • Because there is no endpoint, the pasted email has no destination.

Demonstration data is safe by design

  • Every built-in example is fictional.
  • Only reserved domains are used: example.com and example.net.
  • IP addresses come from 192.0.2.0/24, the documentation-only range that cannot be routed.
  • No example link resolves to a real or harmful server.
05 · Testing

Testing, and the bugs the tests caught

The detection logic is covered by 103 automated checks: URL and domain parsing, link classification, attachment classification, header parsing, the arithmetic that produces the score, and a stated expectation for each of the six demonstration emails.

The test suite can be run in a browser from tests/tests.html, or from a command prompt using the JavaScript engine already present on Windows, so no testing framework or package manager is needed.

Expected results of the built-in examples

  • Obvious phishing - 100/100, High Risk
  • Sophisticated phishing - 46/100, Suspicious
  • Fake Microsoft 365 warning - 100/100, High Risk
  • Fake parcel delivery - 100/100, High Risk
  • Fake invoice / BEC - 100/100, High Risk
  • Legitimate email - 0/100, Low Risk

The legitimate example scoring exactly zero is the important one: it proves the rules are not simply firing on everything.

Real defects found and fixed

  • A URL inside a link's visible text was counted as a second link, inflating the link total - fixed by excluding the inside of anchor tags from the plain-text scan.
  • Attachment-name detection was reading filenames out of web addresses such as /report.html - fixed by stripping URLs and HTML before scanning.
  • A legitimate security notice saying "we will never ask for your password" tripped the password rule - fixed with an exemption list for protective wording.
  • Brand-misspelling detection only caught whole-word substitutions - extended so single-character swaps such as micros0ft are caught too.
  • A CSS rule was silently overriding the browser's hidden attribute on the results panel.
06 · Limitations

What this tool cannot do

Being clear about the limits is part of the design, not an afterthought.

Known limits

  • It is a pattern matcher, not a threat-intelligence service. It looks nothing up online and has no idea whether a domain is currently malicious.
  • It only sees what is pasted. An email that is one big image, or whose attachment name never appears in the text, gives it little to work with.
  • Link-text comparison needs the email's HTML source; in plain text there is often no separate "visible text" to compare.
  • The wording rules are written in English, so they will miss equivalent phrasing in other languages.
  • It has no idea whether a message you were expecting is genuine. Context is the user's to supply.

What it will never claim

  • It will not state that an email is malicious.
  • It will not state that an email is safe - a low score is not a clean bill of health.
  • It will not tell a user to click a link or open an attachment to find out.
  • It will not present an unrun check as a passed check.

The user-facing guidance is always to verify out of band: use the organisation's official app or website, or a phone number already held independently.
